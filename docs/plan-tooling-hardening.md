## Контекст

Приложение при первом запуске само скачивает и распаковывает два внешних
бинаря в `downloads/`:

| Инструмент | Источник | Формат |
|---|---|---|
| adb (platform-tools) | `https://dl.google.com/android/repository/platform-tools-latest-{windows,linux,darwin}.zip` | **zip** |
| scrcpy | GitHub API `Genymobile/scrcpy/releases/latest` | `.zip` (Windows) / `.tar.gz` (Linux) |

Ключевые функции — все в `mkdsc/tools.py`:
`safe_extract_zip`, `safe_extract_tar`, `_extract_archive`,
`_download_and_extract`, `_ensure_adb`, `_ensure_scrcpy`, `_verify_tool`,
`_find_exe`, `_select_scrcpy_asset`.

Целевые платформы проекта — **Linux x64 и Windows x64**.

## Задача 1 — восстанавливать бит исполнения после распаковки zip

**Приоритет: блокирующий для Linux.**

### Проблема

`safe_extract_zip` вызывает `zf.extractall(dest_dir)`. Модуль `zipfile` в Python
**не восстанавливает права Unix** — всё извлекается с режимом по умолчанию
(обычно `0644`). adb приезжает именно zip-архивом, поэтому на Linux извлечённый
`downloads/platform-tools/adb` не имеет бита исполнения.

Дальше `_ensure_adb` вызывает `_verify_tool(adb_path, ["version"])`, который
пытается запустить файл и получает `PermissionError`. На чистой Linux-машине без
системного adb приложение не работает вообще.

scrcpy на Linux приходит `.tar.gz`, а `tarfile` права сохраняет (фильтр `data`
ограничивает режим, но бит исполнения не снимает) — там проблемы нет.

### Что сделать

1. В `safe_extract_zip` после `extractall` восстановить режимы из
   `ZipInfo.external_attr`:

   ```python
   mode = member.external_attr >> 16
   ```

   Применять только на POSIX (`os.name != "nt"`), только к обычным файлам,
   маскировать `& 0o777`, пропускать записи с `mode == 0` (архив собран не на
   Unix — поле пустое).

2. Добавить страховку на случай пустого `external_attr`: в `_ensure_adb` и
   `_ensure_scrcpy` перед `_verify_tool` на POSIX доставлять бит исполнения
   найденному бинарю, если его нет (`st_mode | 0o111`).

   Обе меры нужны: первая корректна в общем случае, вторая гарантирует
   работоспособность независимо от того, как собран конкретный архив.

3. Прокомментировать в коде **почему** — иначе следующий рефакторинг
   «упростит» это обратно.

### Критерий приёмки

- На чистой Linux-машине без системного adb приложение стартует, скачивает
  platform-tools и успешно выполняет `adb version`.
- `ls -l downloads/platform-tools/adb` показывает бит `x`.
- На Windows поведение не изменилось.

### Тест

`tests/test_tools.py`: собрать zip, у записи выставить
`external_attr = 0o755 << 16`, извлечь через `safe_extract_zip`, проверить режим.
Пометить `@pytest.mark.skipif(os.name == "nt", ...)` — на Windows режимы файлов
семантики не имеют.

## Задача 2 — запинить версию scrcpy

### Проблема

`SCRCPY_API_URL` указывает на `releases/latest`. В `downloads/` лежит **v3.3.4**,
upstream на момент написания — **v4.1**. То есть каждая новая установка получает
версию, на которой проект не проверялся, а у разработчика всё работает.

Приложение управляет scrcpy через строку аргументов, поэтому переименованный или
удалённый флаг в мажорном релизе ломает продукт у всех новых пользователей.

### Флаги, которые нужно проверить на совместимость с 4.x

Полный список того, что приложение передаёт scrcpy (`mkdsc/web/server.py`,
функции `launch_scrcpy_api` и `start_recording`):

```
--video-bit-rate <v>      --max-size <v>          --keyboard=<uhid|sdk|aoa>
--serial <v>              --select-usb            --select-tcpip
--turn-screen-off         --fullscreen            --no-audio
--record <path>           --no-window             --no-audio-playback
--audio-source=<output|mic>
```

### Что сделать

1. Свериться с changelog scrcpy 4.0 и 4.1 на предмет изменений в этих флагах.
2. Ввести константу с проверенной версией и качать по тегу
   (`releases/tags/vX.Y.Z`) вместо `latest`. Предусмотреть переопределение через
   конфиг или переменную окружения — чтобы пользователь мог поставить свою
   версию, не пересобирая приложение.
3. При старте разбирать вывод `scrcpy --version` и, если версия вне проверенного
   диапазона, писать предупреждение в лог и отдавать его в UI (не блокировать
   запуск — пользователь может знать, что делает).
4. Обновить закреплённую версию до 4.1, если флаги совместимы. Если нет —
   зафиксировать 3.3.4 и завести отдельную задачу на миграцию.

### Критерий приёмки

- Свежая установка на чистой машине получает **предсказуемую** версию scrcpy.
- Несовпадение версии видно в логе и в интерфейсе.

## Задача 3 — проверять контрольные суммы скачиваемых архивов

### Проблема

`_download_file` качает архив и сразу распаковывает. Целостность не проверяется
никак. Zip Slip закрыт, но подмена самого архива (MITM, компрометация зеркала,
редирект) не обнаруживается.

### Что сделать

**scrcpy** — Genymobile публикует в каждом релизе `SHA256SUMS.txt` и подпись
`SHA256SUMS.txt.asc`. Скачивать `SHA256SUMS.txt`, находить строку нужного
ассета, сверять SHA-256 загруженного файла до распаковки. При несовпадении —
удалять файл и падать с внятной ошибкой.

Проверку GPG-подписи `.asc` в эту задачу **не** включать: нужен вшитый публичный
ключ и работа с ключевым хранилищем. Если считаете нужным — отдельной задачей.

**platform-tools** — у Google нет стабильного URL с контрольной суммой рядом с
`platform-tools-latest-*.zip`. Варианты:

- разобрать `https://dl.google.com/android/repository/repository2-3.xml`, где
  публикуются суммы пакетов, и качать по конкретной версии, а не по `latest`;
- либо зафиксировать в коде известную сумму конкретной версии и качать её;
- либо задокументировать разрыв и ограничиться HTTPS.

Решение за исполнителем. **Я не проверял, есть ли в `repository2-3.xml` суммы в
пригодном для этого виде** — это нужно подтвердить перед реализацией, а не
принимать на веру.

### Критерий приёмки

- Битый или подменённый архив scrcpy не распаковывается, ошибка понятна.
- Выбранное решение по platform-tools отражено в `docs/build.md`.

фатальным в принципе.

Клонирование в чистый каталог → `npm run tauri:build:full` → приложение
соединяется с бэкендом.

## Проверка на Linux

Задачи 1 и 4 без реального прогона на Linux x64 закрытыми считать нельзя.
Подойдёт VM, контейнер или WSL2 — для проверки прав на файл и старта бэкенда
проброс USB не нужен, достаточно факта успешного `adb version`.

Минимальный сценарий:

```bash
rm -rf downloads/            # сымитировать чистую установку
python web_panel.py          # должен скачать platform-tools и подняться
ls -l downloads/platform-tools/adb
```

## Чего в этой задаче делать НЕ нужно

- Не трогать HTTP-слой и веб-режим: принято решение переносить бэкенд на Rust,
  вложения сюда будут выброшены (см. `AGENTS.md`, раздел «Архитектурное
  решение»).
- Не начинать порт на Rust — это отдельная работа после стабилизации.
- Не переписывать `_find_exe` и логику поиска бинарей: там есть замечание по
  производительности (рекурсивный обход проекта), но оно не блокирующее и
  относится к другой задаче.
