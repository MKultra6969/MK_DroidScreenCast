# План: порт бэкенда на Rust, веха 1 — «шагающий скелет»

**Статус:** к исполнению
**Ветка:** создать `feat/rust-port-m1` от `fix/tooling-hardening`
**Оценка:** ~500 строк Rust + ~90 строк TS, 1–2 дня
**Цель вехи:** один эндпоинт (`GET /api/devices`) целиком уезжает с HTTP на
Tauri IPC, всё остальное продолжает работать через Python. После этого
перенос оставшихся эндпоинтов — механическое повторение.

Правила репозитория — [`AGENTS.md`](../AGENTS.md). Критично: **никаких
`Co-Authored-By` в коммитах**, изменения в [`CHANGELOG.md`](../CHANGELOG.md),
неочевидные решения комментировать в коде.

## Зачем именно так

Приложение сейчас — три процесса: Rust-оболочка спавнит Python-бэкенд
(19 МБ PyInstaller), фронт ходит в него по HTTP на 127.0.0.1:6969. Порт на Rust
убирает сетевой слой целиком, а вместе с ним — аутентификацию по токену,
хардкод порта, гонку старта, PyInstaller и проблемы упаковки под Linux.

Веха 1 не переносит логику массово. Она строит **механизм**, по которому
переносится всё остальное, и доказывает его на одном реальном эндпоинте.

`GET /api/devices` выбран потому, что задействует всё сразу: поиск бинаря adb,
запуск процесса, разбор текстового вывода, чтение конфига, сериализацию и
высокочастотный поллинг (раз в 5 секунд из `App.tsx`).

## Ключевая идея: `apiFetch` возвращает синтетический `Response`

В `App.tsx` более 40 мест вызывают `apiFetch(...)` и работают с результатом как
с `Response`: `response.ok`, `response.status`, `readJson(response)`,
`response.blob()`, `response.headers.get(...)`.

Чтобы **ни одно из них не пришлось трогать**, роутер после `invoke` собирает
настоящий объект `Response` из результата:

```ts
new Response(JSON.stringify(payload), {
  status: 200,
  headers: { 'content-type': 'application/json' },
});
```

Ошибку Rust-команда возвращает структурой со статусом, роутер превращает её в
`Response` с тем же статусом и телом `{"detail": "..."}` — ровно то, что уже
разбирают `readJson()` и `fileErrorMessage()`.

Это и есть весь фокус миграции. Всё остальное — повторение.

## Задача 1 — каркас Rust-ядра

Сейчас `src-tauri/src/main.rs` — 290 строк, одна команда `mkdsc_api_token`.
Разложить на модули:

```
src-tauri/src/
  main.rs        существующее: спавн бэкенда, окно, resolve_base_dir/resolve_data_dir
  error.rs       ApiError { status: u16, detail: String }
  paths.rs       BASE_DIR / DATA_DIR — та же логика, что в mkdsc/paths.py
  config.rs      чтение config.json (в этой вехе только чтение)
  tools.rs       поиск adb на диске
  devices.rs     запуск `adb devices` + разбор
  api.rs         команды вида api_*
```

### `error.rs`

```rust
#[derive(serde::Serialize)]
pub struct ApiError { pub status: u16, pub detail: String }
```

Команды возвращают `Result<serde_json::Value, ApiError>`. Статусы использовать
осмысленные — те же, что отдаёт FastAPI (400, 404, 409, 500).

### `paths.rs`

Повторить `mkdsc/paths.py`: `MKDSC_BASE_DIR` / `MKDSC_DATA_DIR` из окружения,
иначе — то, что уже вычисляют `resolve_base_dir()` и `resolve_data_dir()` в
`main.rs`. Вынести их сюда, чтобы не дублировать.

Важно: Rust и Python в этой вехе работают с **одним и тем же** `config.json`.
Расходиться в вычислении пути нельзя.

### `tools.rs` — только поиск, без скачивания

Скачивание, контрольные суммы и биты исполнения в этой вехе **не переносить** —
бутстрапом по-прежнему занимается Python, он стартует первым. Rust нужно лишь
найти уже лежащий на диске бинарь, в том же порядке, что и Python:

1. `MKDSC_ADB_PATH` из окружения;
2. `<DATA_DIR>/downloads/**/adb[.exe]`;
3. `<BASE_DIR>/bin`, `<BASE_DIR>/downloads`;
4. `PATH`.

Не копировать из Python рекурсивный обход всего проекта — там известная
проблема с производительностью (обход `node_modules`). Искать точечно в
`downloads/platform-tools/`.

Результат кэшировать в состоянии Tauri (`OnceLock` или `Mutex<Option<PathBuf>>`).

### `config.rs`

Прочитать `config.json`, достать массив `devices`. Только чтение. Запись,
валидация и миграция переносятся в следующих вехах — сейчас за них отвечает
Python, и два процесса, пишущих один файл, гарантированно подерутся.

## Задача 2 — команда `api_devices`

Зеркалит `GET /api/devices` (`mkdsc/web/server.py:360`). Контракт:

```json
{
  "saved":     [ { "name": "...", "ip": "...", "port": "5555", "connection_type": "wifi", "last_used": "..." } ],
  "connected": [ { "serial": "...", "status": "device" } ],
  "timestamp": "2026-08-11T12:34:56.789012"
}
```

`saved` — как есть из `config.json`. `connected` — разбор `adb devices`.
`timestamp` — ISO-8601. Фронт (`normalizeDevices` / `normalizeSavedDevices` в
`App.tsx`) терпим к лишним полям, но **имена и типы существующих менять нельзя**:
`port` приходит строкой, `status` — строкой.

Запускать через `tokio::process::Command` (tokio уже приходит с Tauri), не через
`std::process` — иначе заблокируется поток рантайма. На Windows не забыть
`CREATE_NO_WINDOW`, в `main.rs` уже есть `set_no_window()`.

### Разбор `adb devices` — три ловушки

Питоновский вариант (`mkdsc/tools.py:697`) опирается на `text=True`, который
сам нормализует переводы строк. В Rust этого нет, поэтому:

1. **`\r\n`.** Читать stdout как байты, декодировать lossy, резать по `\n` и
   **обязательно** обрезать `\r` с конца строки. Иначе на Windows `status`
   станет `"device\r"`, и в UI появится «device» с переносом, а сравнения
   вроде `status === 'device'` начнут молча не срабатывать.
2. **Шум демона.** Первый запуск печатает
   `* daemon not running; starting now at tcp:5037` и `* daemon started
   successfully`. Строки без табуляции пропускать.
3. **Больше одной табуляции.** Использовать `splitn(2, '\t')`, а не split по
   всем — в Python аналогичный код упал бы с `ValueError`.

Первую строку (`List of devices attached`) пропускать. Пустой вывод — пустой
список, не ошибка.

### Тесты

нормальный вывод, `\r\n`, шум демона, `unauthorized`, `offline`,

## Задача 3 — роутер в `apiFetch`

Файл `frontend/src/lib/api.ts`. Сейчас `apiFetch` (строка 63) всегда идёт в
`fetch`. Добавить перед этим проверку маршрута.

Требования:

- Роутер работает **только** когда `isTauri()`. В браузере (`python
  web_panel.py`) ничего не меняется и всё идёт по HTTP. Это обязательное
  свойство: веб-панель должна остаться рабочей до конца миграции.
- Таблица маршрутов вида `"GET /api/devices" → "api_devices"`. Сразу заложить
  разбор query-строки и параметров пути (`/api/devices/{ip}/{port}`) — дальше
  почти все эндпоинты их используют, но в этой вехе достаточно точного
  совпадения по пути.
- Путь разбирать через `new URL(path, 'http://x')`, чтобы отделить `pathname`
  от `searchParams`, а не регулярками.
- Аргументы в команду передавать структурой `{ query, body }`, где `body` —
  уже разобранный JSON из `init.body`, если он есть.
- Незнакомый путь — молча уходит в `fetch`. Никаких исключений: это гарантия,
  что непереехавшие эндпоинты продолжают работать.
- `timeoutMs` для IPC-веток можно игнорировать (таймаут задаётся на стороне
  Rust), но `apiFetch` обязан остаться совместимым по сигнатуре.

`wsUrl()` и WebSocket в этой вехе **не трогать** — они переезжают на события
Tauri в отдельной вехе.

### Критерий приёмки

В десктопной сборке во вкладке Network devtools **нет запросов к
`/api/devices`**, при этом список устройств в UI живой и обновляется. Остальные
запросы (`/api/config`, `/api/i18n`, `/api/recording/status`) продолжают идти по
HTTP.

Контрольная проверка: временно вернуть в Python на `/api/devices` ответ 500 —
десктопное приложение не должно этого заметить, а веб-панель должна сломаться.
Это доказывает, что маршрут действительно уехал.

## Задача 4 — вырезать macOS

Решение владельца: поддерживаются только **Linux x64 и Windows x64**.

- `.github/workflows/release.yml` — убрать две matrix-записи `macos-latest`
  и связанный с ними `targets:` в шаге установки Rust.
- `docs/build.md` — убрать раздел macOS; заодно зафиксировать нижнюю границу
  glibc: релизы собираются на `ubuntu-22.04`, то есть требуется Debian 12 /
  Ubuntu 22.04 или новее.
- В Rust ветки под macOS не добавлять.
- **Python не трогать.** Остатки `darwin` в `mkdsc/tools.py` безвредны и будут
  удалены вместе с Python — тратить на них коммит не нужно.

## Проверка

Доступны WSL2 и отдельный ноутбук с Linux — использовать оба, они закрывают
разное.

**WSL2** — логика: `cargo test`, сборка, разбор вывода adb.

**Ноутбук с Linux** — то, чего WSL2 не покажет: реальная сборка `tauri build`,
запуск собранного пакета, как выглядит интерфейс в WebKitGTK (а не в WebView2),
живое устройство по USB.

Отдельно на ноутбуке проверить то, что на Linux **никогда не запускалось**
(к этой вехе не относится, но раз машина под рукой — зафиксировать результат
в отчёте):

- собранный `.deb`/`.AppImage` вообще стартует;
- интерфейс не разъехался в WebKitGTK;
- scrcpy открывает своё окно из упакованного приложения;
- выбор папки (диалог) работает через XDG-портал;
- остановка записи по `SIGINT` не портит файл.

Обязательно на Windows тоже: разбор `\r\n` — единственное место, где легко
сделать «работает на Linux, ломается на Windows».

## Чего в этой вехе делать НЕ нужно

- Не переносить остальные эндпоинты. Веха доказывает механизм, а не сокращает
  Python.
- Не переносить скачивание инструментов, контрольные суммы и биты исполнения —
  этим занимается Python, он стартует первым.
- Не трогать WebSocket и `wsUrl()`.
- Не давать Rust **писать** в `config.json`, пока Python жив.
- Не редизайнить контракт. Зеркалим REST один в один — решение зафиксировано в
  `AGENTS.md`, обсуждать заново не нужно.
- Не добавлять тест-раннер во фронтенд (его в проекте нет). Логику разбора
  покрывают тесты на стороне Rust.
